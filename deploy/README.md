# Deterministic deployment

Tooling that deploys ONCHAINID, T-REX, the shared compliance modules and the UtilityChecker at the same
addresses on every chain, through Safes, and hands every role to them. It follows OpenZeppelin's review of the
T-REX deployment guidelines (16 November 2026). The scripts are in `scripts/deploy/`, the tests in
`test/unit/deploy/` and `test/fork/`.

## How addresses are made

| What | How | Sent by |
|---|---|---|
| Genesis Deployer (a copy of CreateX) | CREATE2 through the keyless anchor `0x4e59…956C` (code hash checked) | anyone |
| Safe v1.4.1 contracts | canonical addresses; deployed through the Safe Singleton Factory where missing | anyone |
| Deployment, Protocol Admin, Upgrade Council, Operations Safes | `SafeProxyFactory.createProxyWithNonce`, with a `setup` that is the same on every chain (SafeToL2Setup, no refund) | anyone |
| 7 libraries, every implementation | CREATE2 through the Genesis Deployer with a permissionless salt (the address commits to the code) | anyone |
| Both AccessManagers, IdentityFactory, ReputationRegistry, ERC734Validator, IdentityUtilities proxy, TREXImplementationAuthority, TrustedGatewayRegistry, TREXFactory, 3 module proxies, UtilityChecker, RoleRevoker | CREATE3 through the Genesis Deployer, salt bound to the Deployment Safe | Deployment Safe |
| 5 suite beacons, UtilityChecker proxy | CREATE at a known nonce of their deployer | (with the above) |
| Identity beacon | OpenZeppelin Create3 inside the IdentityFactory (`initializeBeacon`) | Bootstrap Operator |

`addresses/mainnet.json` lists every row: contract, method, salt, init code hash, expected address.

### Onboarding a chain later

Only the Deployment Safe has to be the same everywhere: the CREATE3 salts are bound to it, so its owners (in
order), threshold and salt nonce are frozen. The three governance Safes enter no contract address. A chain added
years later should therefore get a `config/<env>.json` with the governance owners of that day: every protocol
contract, suite and identity still lands at the usual address, only the three governance Safe rows move, and those
new Safes receive the roles (`ForkAddressEquality.test_laterChainWithCurrentGovernanceOwners`).

## Files

| Path | What |
|---|---|
| `config/<env>.json` | Safes (owners in order, threshold, salt nonce), Bootstrap Operator, salts, release, delay tiers |
| `addresses/mainnet.json` | the address table, generated by `AddressTable.s.sol` from the config and the build, with the commit it was generated at: the pin. Reviewers and signers check it, and the broadcasting scripts refuse to run when the build no longer gives it. Other envs share it (only `chainId` differs) or generate theirs on demand |
| `vendor/` | third-party bytes our build cannot produce, with their provenance in `vendor.json` (see below) |
| `../deployments/<env>/` | run output, gitignored: Safe batches, `verification.json` |

### Where the bytecode comes from

- **T-REX and ONCHAINID:** Foundry's build output, nothing stored. T-REX from `out/`; the eight ONCHAINID contracts
  from `out-onchainid/` (the `onchainid` profile, via_ir, as upstream ships them; IdentityFactory is over EIP-170
  without it). A pinned commit gives the same bytes on every build, and the address table records each row's init
  code hash. A single `forge build` with `compilation_restrictions` was tried: it gives the same bytes, but a clean
  build takes 404 s instead of 76 s and coverage reports drop to about 92 % lines because importing tests compile
  via IR, so the separate profile stays.
- **CreateX** (`vendor/createx.hex`, 24 KB): our own copy is the Genesis Deployer and every address derives from its
  creation code, so it must never change. `BytecodeStore.CREATEX_INITCODE_HASH` pins it and is checked on every read.
  It rebuilds bit for bit from pcaversaccio/createx `6e853597` (solc 0.8.23, paris, 10,000,000 runs, no IR,
  `bytecode_hash = "none"`): `sh deploy/vendor/check-createx.sh`. Building it in this repo instead would need the
  global solc pin and metadata settings changed for everyone.
- **Safe v1.4.1** (`vendor/safe-1.4.1/`): on a chain that has the canonical contracts (every fork test, every real
  target) no Safe file is read; the SafeProxy creation code comes from the chain's SafeProxyFactory and
  `ForkDeployment` checks the vendored copy equals it. The files are read only (a) to deploy the contracts where a
  chain lacks them, which is the bare local chain of the CI tests, and (b) to predict Safe addresses offline for the
  address table. Kept: Safe, SafeL2, SafeProxyFactory, CompatibilityFallbackHandler (the Safes' fallback handler),
  MultiSendCallOnly (Transaction Builder batches), SafeToL2Setup (the chain-independent setup), SafeProxy (address
  prediction). CreateCall was dropped: nothing uses it.
- **Anchor runtime** (`vendor/create2-factory-runtime.hex`, 69 bytes): etched on the bare local chain only.

`config/mainnet.json` and `config/baseSepolia.json` hold **placeholders** (owners `0x…1001` and so on). They differ
only in `chainId`, so their address tables are identical. See "Frozen values" below.

## Running a deployment

Every script checks the chain id against the config and the build against `addresses/<env>.json` (naming the
differing rows and the table's commit), probes every step first, skips what is already done and stops before sending
anything if any expected address holds something unexpected. Any run can be repeated or resumed. The table check
is skipped on a local chain (31337) and in tests. A live deployment can only be verified from the commit its table
was generated at, since CREATE2 addresses are computed from the build; upgrades check only the rows they talk to
(managers, authority, Safes), as the new release's implementations differ by design.

```sh
# 0. Build both profiles, and write the address table when cutting a release
forge build
FOUNDRY_PROFILE=onchainid forge build --sizes \
  dependencies/onchain-id-develop/contracts/factory/IdentityFactory.sol \
  dependencies/onchain-id-develop/contracts/Identity.sol \
  dependencies/onchain-id-develop/contracts/IdentityUtilities.sol \
  dependencies/onchain-id-develop/contracts/proxy/IdentityUtilitiesProxy.sol \
  dependencies/onchain-id-develop/contracts/modules/validators/ERC734Validator.sol \
  dependencies/onchain-id-develop/contracts/modules/executors/KeyApprovalModule.sol \
  dependencies/onchain-id-develop/contracts/reputation/ReputationRegistry.sol \
  dependencies/@openzeppelin-contracts-5.7.0/utils/cryptography/verifiers/ERC7913WebAuthnVerifier.sol
# The table records the commit it was built from, so generate it from a committed tree (git status clean) and
# commit it on its own: "check out that commit" must lead to a tree that rebuilds it.
forge script scripts/deploy/AddressTable.s.sol --sig "run(string,string)" mainnet $(git rev-parse HEAD)
forge script scripts/deploy/AddressTable.s.sol --sig "check(string)" mainnet   # the build still gives the table

# 1. Genesis: Genesis Deployer, Safe contracts, the four Safes (any funded key)
forge script scripts/deploy/Genesis.s.sol --sig "status(string)" mainnet --rpc-url $RPC
forge script scripts/deploy/Genesis.s.sol --sig "run(string)" mainnet --rpc-url $RPC --broadcast

# 2. Protocol: CREATE2 rows are broadcast; CREATE3 rows are written as Safe Transaction Builder files in
#    deployments/mainnet/batches/. Load them in the Deployment Safe, sign, execute, run the same command again.
forge script scripts/deploy/DeployProtocol.s.sol --sig "run(string)" mainnet --rpc-url $RPC --broadcast

# Wait for finality between phases on rollups: each phase reads the chain to decide what is left, so a phase run
# on unfinalized state that is later reorganized away simply finds those steps pending again on the next run.

# 3. Configure (Bootstrap Operator): handover steps 1 to 5
forge script scripts/deploy/ConfigureAndHandover.s.sol --sig "configure(string)" mainnet \
  --rpc-url $RPC --broadcast --sender $BOOTSTRAP

# 4. Five days later: verify, scan every governance log since the deployment block (the Bootstrap Operator's own
#    holdings exempt), renounce everything (steps 6 and 7), then scan again with no exemption. $DEPLOY_BLOCK must be
#    at or before both managers' deployment: the script proves neither had code at $DEPLOY_BLOCK - 1. The last
#    argument is the block span per eth_getLogs request.
forge script scripts/deploy/ConfigureAndHandover.s.sol --sig "finalize(string,uint256,uint256)" mainnet $DEPLOY_BLOCK 10000 \
  --rpc-url $RPC --broadcast --sender $BOOTSTRAP

# Verify at any time (read-only)
forge script scripts/deploy/VerifyDeployment.s.sol --sig "run(string)" mainnet --rpc-url $RPC
# After proxy or identity beacon upgrades, list the new implementations (any other one fails):
forge script scripts/deploy/VerifyDeployment.s.sol --sig "run(string,address[])" mainnet "[$NEW_IMPL]" --rpc-url $RPC
# Every role holder and mapping (step 6): manager grants (pending ones too), function mappings (an unlisted selector
# moved off ADMIN, PUBLIC_ROLE included), IdentityUtilities AccessControl grants
forge script scripts/deploy/VerifyDeployment.s.sol --sig "scanGovernance(string,uint256,uint256)" mainnet $DEPLOY_BLOCK 10000 --rpc-url $RPC
```

### Local rehearsal on anvil

anvil ships the anchor but not the Safe Singleton Factory; etch it first. Use `config/local.json`, whose owners
and Bootstrap Operator are anvil's public default accounts.

```sh
anvil
cast rpc anvil_setCode 0x914d7Fec6aaC8cd542e72Bca78B30650d45643d7 $(cat deploy/vendor/create2-factory-runtime.hex)
forge script scripts/deploy/Genesis.s.sol --sig "run(string)" local --rpc-url http://127.0.0.1:8545 --broadcast --private-key $ANVIL_KEY_0
# runLocal executes the Safe steps itself (approveHash from each owner): give it the Deployment Safe owners' keys
forge script scripts/deploy/DeployProtocol.s.sol --sig "runLocal(string)" local --rpc-url http://127.0.0.1:8545 \
  --broadcast --slow --private-keys $ANVIL_KEY_0 --private-keys $ANVIL_KEY_1 --private-keys $ANVIL_KEY_2 --sender $ANVIL_ADDR_0
forge script scripts/deploy/ConfigureAndHandover.s.sol --sig "configure(string)" local --rpc-url http://127.0.0.1:8545 \
  --broadcast --slow --private-key $ANVIL_KEY_6 --sender $ANVIL_ADDR_6
cast rpc evm_increaseTime 432001 && cast rpc evm_mine
forge script scripts/deploy/ConfigureAndHandover.s.sol --sig "finalize(string,uint256,uint256)" local 0 10000 --rpc-url http://127.0.0.1:8545 \
  --broadcast --slow --private-key $ANVIL_KEY_6 --sender $ANVIL_ADDR_6
forge script scripts/deploy/VerifyDeployment.s.sol --sig "run(string)" local --rpc-url http://127.0.0.1:8545
```

## Roles after the handover

| Manager | Role | Holder | Execution delay | Governs |
|---|---|---|---|---|
| Platform | ADMIN | Protocol Admin Safe | 48 h | everything not mapped below |
| Platform | ROLE_MANAGER | Protocol Admin Safe | 48 h | admin of the operational roles: grants are visible 48 h before they apply |
| Platform | ROLE_MANAGER | RoleRevoker | none | revoke-only: any Platform ADMIN holder cuts an operator off at once |
| Platform | GUARDIAN | Protocol Admin Safe | none | cancels VERSION_MANAGER, INTEROP_MANAGER, REPUTATION_MANAGER operations |
| Platform | VERSION_MANAGER | Upgrade Council Safe | 5 days | factory setters, `upgradeBeacon`, `setIdentityTypeModules`, `setTrustedVerifier` |
| Platform | TOKEN_ISSUER | Operations Safe | none | `deployTREXSuite`, `deployTREXSuiteIsolated` |
| Platform | INTEROP_MANAGER | Operations Safe | 24 h | `setTrustedGateway` on the TrustedGatewayRegistry and the IdentityFactory |
| Platform | REPUTATION_MANAGER | Operations Safe | 24 h | ReputationRegistry writes |
| Platform | CLAIM_ISSUER_ADMIN, ISSUER, PUBLIC_AUTHORITY | Operations Safe | none (grant delay only) | identity creation |
| Platform | ASSET_DEPLOYER | TREXFactory | none | token identities |
| Upgrade | ADMIN | Upgrade Council Safe | 5 days | everything not mapped below |
| Upgrade | VERSION_MANAGER | Upgrade Council Safe | 5 days | suite versions, module, UtilityChecker and IdentityUtilities upgrades, IdentityUtilities `grantRole`/`revokeRole`, UtilityChecker ownership |
| Upgrade | GUARDIAN | Protocol Admin Safe | none | cancels VERSION_MANAGER operations |

Grant delays and target admin delays follow the same tiers. The table lives in `scripts/deploy/lib/RoleTable.sol`
and `PlanBuilder.sol` (`_functionRoles`, `_operationalGrants`, `_safeGrants`, `_grantDelays`, `_targetAdminDelays`).
Every role id comes from `RolesLib`, the identity-creation roles included. No function of an Upgrade-manager target
is left on ADMIN, where the guardian could not cancel it.

The handover follows OpenZeppelin's order: the operational roles are granted in step 2, while ADMIN is still their
admin, and ROLE_MANAGER becomes their admin in step 3. The Bootstrap Operator never holds ROLE_MANAGER.

**RoleRevoker** (`scripts/deploy/RoleRevoker.sol`) is a permanent on-chain contract holding a role, so it must be in
the audit scope before mainnet; it is unaudited today. It holds ROLE_MANAGER with no delay and can only
revoke: `revokeRole(role, account)` or `revokeRoles(roles, account)`, callable by whoever holds Platform ADMIN. The
manager limits it to roles whose admin is ROLE_MANAGER. This keeps instant revocation while the Protocol Admin
Safe's own ROLE_MANAGER sits behind 48 h, so it cannot quietly grant itself INTEROP_MANAGER.

## Upgrades and rollback

```sh
# A release is the current checkout's build, published under its own salt
forge script scripts/deploy/Upgrade.s.sol --sig "publish(string,bytes32)" mainnet $SALT --rpc-url $RPC --broadcast
forge script scripts/deploy/Upgrade.s.sol --sig "schedule(string,bytes32,uint8,uint8,uint8)" mainnet $SALT 5 1 0 --rpc-url $RPC
# 5 days later, within a week (the manager's expiry):
forge script scripts/deploy/Upgrade.s.sol --sig "execute(string,bytes32,uint8,uint8,uint8)" mainnet $SALT 5 1 0 --rpc-url $RPC
# Upgrade and rollback together: the rollback republishes what the authority recorded under 5.0.0 as 5.1.1
forge script scripts/deploy/Upgrade.s.sol --sig "scheduleWithRollback(string,bytes32,uint8[3],uint8[3],uint8[3])" \
  mainnet $SALT "[5,1,0]" "[5,0,0]" "[5,1,1]" --rpc-url $RPC
forge script scripts/deploy/Upgrade.s.sol --sig "executeRollback(string,uint8[3],uint8[3])" mainnet "[5,0,0]" "[5,1,1]" --rpc-url $RPC
# Guardian veto (Protocol Admin Safe batch), alone or for an upgrade scheduled with its rollback:
forge script scripts/deploy/Upgrade.s.sol --sig "cancel(string,bytes32,uint8,uint8,uint8)" mainnet $SALT 5 1 0 --rpc-url $RPC
forge script scripts/deploy/Upgrade.s.sol --sig "cancelWithRollback(string,bytes32,uint8[3],uint8[3],uint8[3])" \
  mainnet $SALT "[5,1,0]" "[5,0,0]" "[5,1,1]" --rpc-url $RPC
# Both refuse when nothing is scheduled for the operation they compute (a guardian on another build computes another
# id). Veto by operation id instead: caller, target and data come from the OperationScheduled log, any build works.
forge script scripts/deploy/Upgrade.s.sol --sig "cancelScheduled(string,bytes32[],uint256,uint256)" \
  mainnet "[$OPERATION_ID]" $SCHEDULE_BLOCK 10000 --rpc-url $RPC
# Dry run of the whole path on a fork, nothing broadcast:
forge script scripts/deploy/Upgrade.s.sol --sig "dryRun(string,bytes32,uint8,uint8,uint8)" mainnet $SALT 5 1 0 --fork-url $RPC
```

The authority only accepts a higher version. A rollback never rebuilds an older release (a newer checkout cannot): it
reads the implementations the authority recorded under the previous version (`implementationsFor`) and republishes
them under a new, higher version, through the same 5 days. `scheduleProxyUpgrade` and `executeProxyUpgrade` handle
the UUPS proxies. Every entry first checks the build still gives the governance rows of the table.

## Tests

```sh
forge test --match-path "test/unit/deploy/*"     # no RPC: full deployment on a local chain through the real Safes
forge script scripts/deploy/AddressTable.s.sol --sig "check(string)" mainnet   # the build gives the committed table
TREX_FORK_TESTS=true forge test --match-path "test/fork/*" --threads 1        # Base Sepolia fork, needs ALCHEMY_KEY
TREX_FORK_TESTS=true TREX_FORK_RPC_URL=<Base Sepolia RPC> forge test --match-path "test/fork/*" --threads 1
TREX_FORK_TESTS=true TREX_FORK_ENV=mainnet TREX_FORK_RPC_URL=<mainnet RPC> forge test --match-path "test/fork/*" --threads 1
```

The deploy unit tests need the `onchainid` build (step 0). Without it they skip, with a message naming the command, so
a plain `forge test` on a fresh clone does not fail; CI builds it and sets `TREX_REQUIRE_DEPLOY_TESTS=true`, which
turns that skip into a failure. Fork tests skip themselves unless enabled and are not part of CI. The fork tests run on **Base Sepolia** by default, where the T-REX testnet lives, with
`config/baseSepolia.json`; `TREX_FORK_ENV=mainnet` runs the same suite on an Ethereum mainnet fork with
`config/mainnet.json`, which proves mainnet itself qualifies. They deploy the whole protocol fresh from the
build, ONCHAINID v3 included, so they never depend on contracts already deployed there; only the CREATE2 anchor,
the Safe Singleton Factory and the Safe v1.4.1 contracts must exist, and `ForkDeployment` checks them byte for byte.
The fork block is pinned per chain (`TREX_FORK_BLOCK` overrides it), so the RPC must serve historical state.
`--threads 1` runs one suite at a time, since RPC free tiers (Alchemy's included) answer parallel suites with
HTTP 429. `ForkAddressEquality` replays the deployment on a second fork running as the other chain's id and compares
every address with the table computed from `config/mainnet.json` (the content of `addresses/mainnet.json`, which
`AddressTable.s.sol check(mainnet)` keeps honest).

| File | What it covers |
|---|---|
| `ForkDeployment` | chain qualification, full deployment, size and gas limits, P-256 precompile |
| `ForkResume` | re-run, resume after a partial run, implementation deployed by a stranger, unexpected code |
| `ForkAddressEquality` | same addresses on both target chains, matching the `config/mainnet.json` table; L2 vs L1 Safe singleton; a later chain with current governance owners moves only those three Safes |
| `ForkHandover` | the handover state, every holder and mapping planned (governance log scan), RoleRevoker and 48 h ROLE_MANAGER; schedule, wait, execute; guardian cancel; expiry |
| `ForkSmoke` | suite, identities, mint and transfer after the handover |
| `ForkUpgradeRehearsal` | upgrade then rollback, with only governance and beacon storage written |
| `ForkIncidentResponse` | compromised Operations Safe cut off at once through the RoleRevoker, leaked Bootstrap key, operators kept away from code, guardian cancels a pre-scheduled rollback (cancel tooling), cancels an upgrade and its rollback together, cannot execute; hostile gateway distrust behind 24 h |
| `ForkGovernanceChanges` | new operator scheduled behind 48 h then the grant delay, Protocol Admin moved to a new Safe (96 h), Safe owner rotation, delay reduction behind the 5-day setback, remapping a code function (the known limit) |
| `ForkUpgradesOverTime` | module, UtilityChecker and IdentityUtilities upgrades, identity beacon upgrade with identities intact, upgrade and rollback scheduled together, isolated suite untouched, two releases in a row |
| `ForkLongRun` | six months of suites, identities and transfers with delayed reputation and gateway changes, everyday calls under the 2^24 gas cap, a new chain joining later at the same addresses |

## Frozen values

These become part of deployed addresses and cannot change once anything exists on any chain:

- `genesisSalt`, `create2Salt` (per release), the CREATE3 labels in `PlanBuilder.sol`, the vendored CreateX init code;
- the **Deployment Safe's** owners **in order**, threshold and salt nonce, and the Safe version (v1.4.1): the CREATE3
  salts are bound to it. The three governance Safes are per chain (see "Onboarding a chain later"): their config can
  carry the owners of the day without moving any protocol address;
- the Bootstrap Operator (it is a constructor argument of the managers and the IdentityUtilities proxy, but those
  are CREATE3, so changing it changes no address; it does change who configures).

Replace every placeholder in `config/mainnet.json` and regenerate `addresses/mainnet.json` before any real run.

## Not covered, or decided here

**Audit scope.** Two tooling contracts are deployed on chain and stay there; list them in the audit scope
explicitly, next to `contracts/`:

- `scripts/deploy/RoleRevoker.sol`: permanent, holds ROLE_MANAGER on the Platform manager (revoke-only);
- `scripts/deploy/UtilityCheckerDeployer.sol`: runs once in its constructor (creates the UtilityChecker proxy and
  hands it to the Upgrade manager), keeps no state and no function.

Known limits that need contract changes (out of scope here; most come from OpenZeppelin's report):

- **Not behind proxies:** TREXFactory, TREXImplementationAuthority, TrustedGatewayRegistry, IdentityFactory,
  ERC734Validator and ReputationRegistry use constructors, so a faulty one can only be replaced at a new address.
- **Beacons:** the authority has no beacon of its own, and the identity beacon is owned by the IdentityFactory,
  not by the authority.
- **Storage and versions:** IdentityUtilities storage is not ERC-7201, and most implementations have no `version()`.
- **Issuer side:** issuer admins are granted with no minimum delay, and an isolated suite lets its issuer upgrade
  the suite's manager at once.
- **Gateways:** trust and distrust are the same function, so distrusting a hostile gateway waits INTEROP_MANAGER's
  24 h (`ForkIncidentResponse.test_hostileGatewayDistrustTakesTheConfigDelay`); an immediate distrust needs its own
  function and role. Pending cross-chain link proposals survive a distrust.
- **Six code-changing functions sit on the Platform manager**, because each contract has a single authority:
  the three TREXFactory setters and `IdentityFactory.upgradeBeacon`, `setIdentityTypeModules` and
  `setTrustedVerifier`. They are mapped to VERSION_MANAGER (Upgrade Council, 5 days, guardian). The Protocol Admin
  Safe could still remap them after 5 days: the effective delay is the larger of its 48 h execution delay and the
  targets' 5-day admin delay. Nothing can cancel that, since ADMIN operations have no guardian. Closing this needs a
  contract change. `setIdentityTypePolicy` and `removeIdentityTypePolicy` stay on ADMIN (48 h, configuration of
  who may create identities, not code).
- **UtilityChecker** sets its owner to `msg.sender` in `initialize`. `UtilityCheckerDeployer` (tooling, unaudited)
  creates the proxy and hands ownership to the Upgrade manager in one constructor. The real fix is letting
  `initialize` take the owner.
- **RoleRevoker must be audited before mainnet.** It lives in `scripts/deploy/` like `UtilityCheckerDeployer`, but
  it is a permanent on-chain contract holding a revoke-only power on the Platform manager. The verifier checks it
  points at that manager (`manager()`), which neither the masked code probe nor CREATE3 commits to.
- **`setAuthority` on AccessManaged targets** answers only the current manager, which calls it from its own
  `updateAuthority`. OpenZeppelin hardcodes that to ADMIN, so no function mapping can move it; it is part of the
  ADMIN limit above.
- **RecoveryModule and EASClaimIssuer** are out of scope: RecoveryModule needs `@openzeppelin/accounts`, which this
  repo does not depend on.
- **ONCHAINID bytecode** comes from the vendored `onchain-id` pin (`4c6d074c`), built with `via_ir`
  (IdentityFactory is 25,304 bytes without it, 19,700 with it). Repinning changes every ONCHAINID address.
- **Sizes are tight:** ModularCompliance and Token are close to the 24,576-byte limit.
- **The table belongs to the commit it records.** After a contract change, regenerate it (`AddressTable run`) and
  review the diff; until then the broadcasting scripts refuse to run against that build.
- **Unverified:** that the Safe Transaction Builder accepts files without `meta.checksum` (check once in the UI).

Not covered by this tooling:

- monitoring of the deployed contracts and pending operations;
- a non-canonical address track for chains without the CREATE2 anchor (`Genesis.s.sol status` refuses them);
- the ZKsync testnet check. OpenZeppelin's report found the anchor gives the same address there; what is untested is
  how CreateX's CREATE3 and the nonce-derived rows behave on ZKsync's different contract deployment model;
- a signed per-chain manifest of what was deployed (`verification.json` is written, not signed);
- a storage-layout comparison between releases (run `forge inspect <Contract> storageLayout` on both and diff
  before publishing an upgrade);
- gas under each chain's pricing: gas units are the same on every EVM chain at the same hardfork, so the 2^24 cap
  check holds; the price paid is not modelled. The tests run the repo's `evm_version` (cancun).
